# Known Limitations

Generated: 2026-05-10

- `Fluid2D` defaults to the GPU solver path. CPU simulation exists only as a fallback when no valid sokol graphics context is available, headless mode is active, or `FluidSettings::useGpu` is disabled.
- The GPU fluid path currently covers splat, velocity/density/temperature texture injection, advection, optional vorticity, optional buoyancy, obstacle masks, divergence, Jacobi pressure solve, projection, and GPU density/velocity/pressure/temperature/combined/LIC display.
- `OpticalFlow` supports GPU texture input through `update(const tc::Texture&, float)`. Tests still exercise procedural CPU flow because they run without an app graphics context.
- `example-camera-fluid` now uses real `tc::VideoGrabber` texture input directly into GPU optical flow, with procedural fallback only when camera/permission/GPU input is unavailable.
- Bridge classes provide procedural fallback injection APIs, generated bridge shader assets, and GPU external texture wiring for velocity, density, temperature, and combined bridge injection.
- `BridgeSettings::invert`, `useAlphaAsMask`, `mirrorX`, `mirrorY`, `maskSource`, `maskSoftness`, and `maskGamma` now drive the GPU bridge shader path. Exact ofx GUI parameter binding remains partial.
- `ParticleFlow` defaults to GPU state textures, a GPU update pass, and GPU particle drawing. CPU particles remain fallback when GPU is unavailable. First-pass flow, attractor, and impulse variants are available.
- GPU particles are intentionally a first complete TrussC/sokol implementation. They now include shader-side procedural spawn seeds plus first-pass age/lifespan/mass-aware movement, draw sizing, and birth-from-velocity controls, but do not yet cover every PixelFlow/ofxFlowTools particle variant such as collision, cohesion, sprite trails, optical-flow capture particles, and dam-break style examples.
- `ParticleFlow::spawn()` now applies same-frame GPU spawn requests independently. It still uses probabilistic texture-particle respawn rather than PixelFlow's exact Java/OpenGL particle shader layout.
- `AverageFlow` now covers first-pass ROI average, watcher events, bounded history, and settings serialization. Exact ofxGui parameter panels, persistent XML format, and mesh-based graph styling from ofxFlowTools remain partial.
- `SplitVelocity` now has a fuller GPU graph with raw positive/negative split texture, normalized texture, decayed trail texture, visual output, and split field overlay drawing. Exact ofx geometry-shader/mesh rendering remains partial.
- Extension helper shader passes now cover colorize luminance/velocity/gradient, decay, dilate, erode, inverse warp, vector normalization, ease, and time blur. `FlowHelperPipeline` wraps them into reusable high-level fullscreen pipelines.
- `Fluid2D` can separate simulation resolution from GPU visualization/output resolution through `FluidSettings::outputResolutionScale`. The simulation itself still uses a single velocity/density/temperature grid, so exact ofxFlowTools HD shader-family parity is still pending.
- All requested example directories are centralized under `examples/` and build on macOS. Current app examples use GPU fluid by default; tests intentionally exercise CPU fallback because they run without an app graphics context.
- 2026-06-08 startup screenshot review found no black screens, stale texture bindings, or obvious wrong-output defaults across the 18 current examples. This was a startup-state visual audit, not a full reference-parity interaction pass for every control mode.
- Exact GPU ping-pong/custom-render streamlines, richer reference-matched field/GUI styling, and PixelFlow multiple-fluid examples are still tracked in `REFERENCE_GAPS.md`.
- PixelFlow `Fluid_LiquidText`, `Fluid_LiquidPainting`, `Fluid_StreamLines`, and `Fluid_CustomParticles` now have first-pass CFD parity examples, but broader Computational Fluid Dynamics examples such as Verlet particle collision follow-up tuning, velocity encoding, multiple fluids, and texture transfer remain partial or missing.
- `example-fluid-physarum-trails` preserves the core OpenProcessing/GPU-IO Physarum particle-trail fluid effect through tcxFlowTools `Fluid2D`, GPU particle position/age ping-pong, shader-side velocity sampling, and GPU trail fade/deposition. It does not port GPU-IO's exact layer/program layout, CanvasCapture recording, PNG save path, or byte-for-byte shader behavior. CPU velocity readback remains fallback/comparison only; larger project uses should still validate particle counts and backend-specific float render-target behavior on the target platform.
- Exact reference geometry-shader/mesh details and byte-for-byte shader behavior remain explicit follow-up work. Current shader ports prioritize cross-platform sokol behavior and matching the core visual effect over one-to-one GLSL/OpenGL parity.
- PixelFlow SoftBody2D cloth now has an independent first-pass implementation in tcxFlowTools. SoftBody2D playground, chain, connected bodies, differential growth, liquid/collision systems, and SoftBody3D remain missing.
- PixelFlow Skylight, post-processing, anti-aliasing, Shadertoy-style wrappers, sampling, and geometry/util families are explicit parity scope after the 2026-05-13 reference clarification, but they are not yet implemented.
- Only the current macOS checkout is being tested in this pass. Windows, Linux, Web, iOS, and Android remain unverified.
- No TrussC core API was modified in this pass.
